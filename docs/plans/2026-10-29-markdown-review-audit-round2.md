# Markdown 批注功能:第二轮审计与修复方案

日期:2026-10-29。审计对象:`feature/markdown-artifact-annotations` 的 HEAD `ca14e3fd`(第一轮 hardening 收尾后的版本)。

存放规则同第一轮:本文档只存放在独立分支 **`docs/markdown-review-hardening-plan`**;功能分支工作区里的同路径副本是**未跟踪的本地副本**,只供阅读审阅,不随 PR 提交。

读法:每条问题统一按 **【功能】→【触发场景】→【现在会发生什么】→【使用影响】→【修复方向(抽象)】→【建议】→【修复后的样子】→【影响与代价】** 书写。代码位置只作为证据行;修复方向只讲抽象方法,不落到函数或参数级细节。第 3 节汇总"修完之后整体是什么样、行为有什么变化、代价是什么"。

本轮结论:**第一轮 9 个问题里 7 个已闭环**,性能只做完了"影响判断/跨文件不扇出",**"每键全量刷新"的另一半仍在**;第一轮问题 2 的"关闭标签懒回收"建立在一个**不成立的前提**上,本轮已重新拍板(关闭标签即放弃未发送草稿,配额 200→500);另外发现 6 类新问题(线程边界、失联批注、错误语义、首帧、资源寿命、收尾项)。2026-10-29 已按批注确认全部决策,见 §4。

## 0. 功能地图(速览)

| 部分 | 位置 | 作用 |
| --- | --- | --- |
| 预览浮层 | IDE 原生 Markdown 预览面板 | 注入脚本/样式,在渲染 HTML 上叠加高亮、工具条、弹窗 |
| Java 服务 | IDE 端,项目级 | 保存批注、设置开关、维护"待发草稿批次"、与预览/聊天桥接 |
| 聊天前端 | CC GUI 输入框 | 批注草稿卡片;发送时打包进消息 |

功能默认**关闭**;设置页有 4 个开关(enabled / autoAddToChat / autoDeleteAffected / persist)。未开启时阅览者看不到任何批注入口。

## 1. 第一轮结论复核

### 1.1 已闭环

- **1a 关闭时零注入**:关闭状态下不再为预览创建浮层,也不再注册监听。
- **1c 语言缓存**:语言偏好改为内存缓存,写语言时显式失效。
- **1d 条件通知**:面板保存上一帧影子副本,状态未变不发包;影响判断只统计当前文档的批注。
- **问题 3**:标记完成不再隐式打开 persist。
- **问题 5**:选择聊天改为"处理中回执 + 幂等重试",8 秒假失败与重复加入已消除。
- **问题 6/7**:坏请求立即回错误;错误以键跨层传递,由浮层词典翻译。
- **问题 9**:完成/删除批注会撤回其自动草稿,发送前再过滤一次。
- **问题 10**:提交时先验证目标再清空输入。
- **问题 11**:聊天区/设置页的 `markdownReview.*` 已补齐 10 种语言。
- **问题 4/8**:`verifyPlugin` 双目标(IU 262 / IC 233)判定 Compatible,无内部 API 命中。

### 1.2 部分闭环 / 前提需修正

- **问题 1b(每键开销)**:影响判断与跨文件抑制已落地,但**编辑之后的"预览回传同步"入口绕过了影响判断**,每键仍会做一次完整重算、序列化与全文图表扫描(见 §2 R1);第一轮标注的"合并窗口"实际未实现。
- **问题 2(草稿回收)**:会话切换路径已闭环;但**关闭聊天标签**路径依赖"标签存档可恢复"的前提,而主动关闭标签会删除该标签的存档(见 §2 R3),本轮已重新拍板。
- **上一轮承诺的顺手项**:选择聊天弹窗仍使用已废弃 API(上一轮记录为"问题 5 重构时一并替换");410 行开发计划文档仍在功能分支中(见 §2 R9)。

## 2. 本轮问题清单

### R1(P0)开启功能后,打字仍是"每键一次全量刷新"

**【功能】** 预览浮层的批注定位与刷新。

**【触发场景】** 开启批注功能后,在 IDE 编辑器里修改任意 .md 文件——哪怕这个文件**一条批注都没有**。每敲一个字符都会触发。

**【现在会发生什么】**

- 编辑器里每改一次文档,原生预览会重绘一次;浮层脚本在每次重绘后都向后端回传一次"同步"。
- 后端收到"同步"后先做一次批注位置核对,再走一次完整状态刷新:序列化该文件全部批注、比较影子副本、把整篇文档从头到尾扫描一遍找 Mermaid 图、最后推给预览页面。
- 完整状态的 payload 含"文档版本号",每次按键必变,所以"状态未变就不发"的影子比较在这条路径上**永远不成立**,必然走完整帧。
- 之前的影响判断(编辑点在所有批注之后 → 什么都不做)只在"编辑事件"这条入口生效,"预览回传同步"这条入口不受它约束。
- 结果:一次按键仍至少触发一轮与**文档长度 + 批注数量**成正比的完整工作,且发生在 IDE 的界面线程上;打字快时多轮排队。

**【使用影响】**

- 大文档(几万到几十万字符)或批注较多时,连续输入可能出现输入/滚动不跟手、CPU 占用升高。
- 功能开启后,"打字"这个最高频动作的代价随文档变大而变大;这正是第一轮问题 1 想消掉、但目前只消掉一半的部分。
- 没有批注的文件也付同样的成本,因为整轮工作的触发条件是"文档变了",而不是"批注需要更新"。

**【证据】** 预览重绘后无条件回传同步(index.ts:450-455);同步入口不做功能开关或影响判断、末尾无条件刷新(NativeMarkdownAnnotations.java:204-213、:317);完整刷新与全文图表扫描(:454-489、:485);影子副本比较依赖 payload 相等(:472-484);项目级广播(MarkdownReviewService.java:753-762,面板监听在 NativeMarkdownAnnotations.java:60-61)。

**【修复方向(抽象)】**

1. **单一刷新入口**:无论刷新来自"编辑事件"还是"预览就绪/同步事件",都先经过同一个"这次需要什么级别的刷新"的判断;同步事件只回答"页面是否已经追上文档",不负责触发重算。
2. **追平前只同步状态**:以**原生预览的渲染结果**作为"是否追上文档"的判据;在页面还没追上文档、用户仍在连续输入的阶段,只同步时间戳与"是否落后",不推送批注明细、不做图表扫描;原生预览刷新完成、页面追平后再做一次完整刷新。浮层在"落后"状态下本来就不渲染高亮,所以这样做对用户没有可见损失。
3. **连续有影响的编辑合并**:把短时间内的多次"有影响"合并成一次推送。时间窗只做合并器,不作为触发条件;主触发始终是"原生预览已追平文档"。
4. **成本与内容无关**:没有批注的文件,除"更新版本号/落后状态"外不应产生任何计算。

**【建议】** 采纳 1–4。验收标准:开启功能后连续输入 N 个字符,后端"完整刷新"次数与文档长度、批注数量无关(无批注文件为 0 次完整刷新);跨文件不扇出(第一轮已具备)。

**【修复后的样子】** 以 IDE 原生预览的刷新完成为锚点:你在编辑器里打字时,原生预览照常实时更新;我们的覆盖层在"原生预览已经追上文档"之后再做一次完整刷新。连续输入期间只下发"页面落后"状态,覆盖层暂时隐藏,不做重算、不抢在原生预览之前刷新;编辑点在所有批注之后,或文件没有批注时,不产生与文档长度相关的计算。停止输入、原生预览刷新完成后,高亮与批注标记立即跟上;跨文件仍然互不打扰。

**【影响与代价】** 覆盖层始终跟随原生预览的节奏,不会让 IDE 自己的渲染等待我们;连续输入期间批注位置最多"晚一拍"更新(当前实现本来就在页面落后时隐藏高亮,不新增可见延迟);合并窗口只是可选的合并优化,不会引入新的可见延迟。代码层面刷新入口收敛为一处,后续改动不容易再出现"某条路径绕过判断"的情况。

### R2(P1)关闭功能后,已打开的预览仍有每键同步往返

**【功能】** 功能开关的实际效果。

**【触发场景】** 曾经开启过批注功能、预览一直开着,随后在设置页把功能关掉,继续编辑这个 .md。

**【现在会发生什么】**

- 关闭后浮层确实会隐藏,也不会再显示任何内容;但已经注入到预览页面的脚本不会卸载。
- 于是每敲一个键,预览页面仍然向后端发一次"同步",后端仍然做一次位置核对,只是最后因为"功能已关"而不推送状态。
- 第一轮 1a 的承诺是"关闭后不再有任何每键开销";严格说只兑现了"不再发包/不再画浮层",没有兑现"不再产生工作"。

**【使用影响】**

- 关闭功能后仍有一部分不可见的按键成本(一次预览→Java 的往返 + 一次位置核对),虽然比开启时小,但与"关闭即零成本"的预期不符。
- 对从不开启功能的用户没有影响(从头就不会注入脚本);受影响的是"开启后关闭"的用户。

**【证据】** 关闭状态下的完整刷新早退(NativeMarkdownAnnotations.java:458-464);同步入口不看开关(:204-213);预览页面每次重绘仍回传同步(index.ts:450-455)。

**【修复方向(抽象)】** 功能关闭时,在桥接入口处直接短路:不核对、不刷新、不回应业务请求;重新开启时由"设置变更"事件主动补一次完整状态。若希望更彻底,可在关闭时让页面侧停止发起同步。

**【建议】** 采纳。验收标准:功能关闭后编辑文档,后端收到的桥接请求为 0,或虽有请求但完全不做工作(二者取其一,以可观测计数为准)。

**【修复后的样子】** 关闭开关后,继续编辑不会有任何批注相关的后台工作,界面保持安静;对已经加载过浮层的预览,重新开启后立即恢复,不需要重开预览。首次开启时"已有预览需重开一次"的既有约束不变。

**【影响与代价】** 关闭状态真正等于"零成本";开关切换对已加载预览即时生效。代价只是重新开启时补一次完整状态推送,可以忽略。

### R3(P0,已拍板)关闭聊天标签后未发送草稿无人回收;配额 200→500,满额改为拒绝新增

**【功能】** "加入 CC GUI"的待发草稿登记与配额。

**【触发场景】**

- 把批注加入聊天草稿、还没发送,直接关闭这个聊天标签页;
- 或者长期使用后配额接近上限。

**【现在会发生什么】**

- 前端在窗口销毁前不会给后端发"这些草稿不要了"的回执。
- 后端有意不在窗口销毁时清理,理由是"标签的 reviewTargetId 会被存档,重开标签能恢复草稿"。
- 但实际关闭路径是:关闭标签 → 先删除该标签的存档(含 reviewTargetId)→ 再销毁窗口。重开的标签是**新的身份**,旧批次永远等不到认领。
- 这些批次只能等配额满时被"驱逐"回收(当前上限 200,本轮决定提高到 500);persist 开启时会跨重启一直写在工作区文件里。
- 驱逐顺序是三层:① 已终态(已送达/已提交)的最旧记录 → ② 主人已消失(标签已关闭)的最旧未确认批次 → ③ 任意最旧的未确认批次。**澄清:驱逐不是"正常草稿先于孤儿被清理"——前两层一定先处理孤儿,第三层只有在"一个孤儿都没有"时才会动到活跃草稿**;也就是说,只有当所有未确认批次都属于仍打开的聊天时,才可能**静默丢掉用户可见的未发送内容**。

**【使用影响】**

- 用户主动关闭标签,以为草稿已随标签丢弃,实际仍占用配额与存储。
- 配额里的"幽灵数据"会挤占正常草稿的位置;好消息是驱逐会**先**清理这些孤儿,但若没有孤儿、配额全是活跃草稿,第三层仍可能让另一个聊天里的草稿凭空消失,且没有任何提示。
- 第一轮的"永不锁死"目标达成了,但代价是引入了"静默丢数据"的新风险。

**【证据】** 窗口销毁不做清理、注释声称身份可恢复(ClaudeChatWindow.java:2999-3010);关闭标签的确认与存档删除(ClaudeSDKToolWindow.java:389-408,其中 :401 删除该标签存档);存档删除实现(TabStateService.java:127-141);配额驱逐与第三层淘汰(MarkdownReviewService.java:576-585、:598-611)。

**【修复方向(抽象)】**

1. **先定义产品语义**:推荐"**用户主动关闭聊天标签 = 放弃该标签未发送的草稿**"(用户已经通过关闭确认框明确表达意图);而"IDE 整体关闭/重启"仍保留草稿恢复能力。两类事件要在实现上被区分开,只对前者回收。
2. **回收时机**:在"标签被确认关闭"的事件上回收该标签名下所有未确认批次,而不是在窗口销毁时(销毁也发生在 IDE/项目关闭,不能一刀切)。
3. **配额与耗尽原则(已拍板)**:上限从 **200 提高到 500**;驱逐只保留"已终态"和"主人已消失"两类,移除"淘汰任意活跃草稿"的第三层。若满额且没有可回收的无主数据,则**拒绝新增并明确提示**:"草稿已满(500),请先提交批注或清理草稿"。不得静默淘汰用户可见的数据。
4. 若产品上坚持"关闭标签后仍可恢复",则需要把草稿归属从"标签存档"提升为独立的持久登记(与标签生命周期解耦);这是一项更大的改动,需要单独评估。

**【建议】**(2026-10-29 已拍板)采纳 1–3:关闭标签即放弃未发送草稿;配额上限调到 500;满额只回收无主数据,否则拒绝新增并提示。第 4 条(关闭后可恢复的独立登记)不采纳。

**【修复后的样子】** 关闭聊天标签后,该标签名下未发送的草稿立即从配额和持久状态中消失,其他聊天不受影响;配额上限提高到 **500**;满额时先回收孤儿草稿,若仍有 500 条活跃草稿,则明确提示"草稿已满(500),请先提交批注或清理草稿",不会静默淘汰任何用户可见的草稿;IDE 重启后,仍然打开的标签仍能恢复草稿。

**【影响与代价】** 用户可见的变化是"关闭标签 = 放弃未发送草稿";建议在关闭确认框里仍有未发送草稿时给出明确提示,避免用户误以为还能恢复。配额提高后,正常使用几乎不会碰到上限;真正满额时从"静默淘汰"改为"拒绝并提示",需要聊天输入区提供可操作的清理入口。好处是持久化数据与真实使用一致,不再有看不见的配额占用。

### R4(P1)后台修改文档时,自动撤回/刷新可能触碰界面线程

**【功能】** autoDeleteAffected(原文被改动后自动删除批注并撤回草稿)与预览刷新。

**【触发场景】** 自动删除开启,批注覆盖的原文被"不是用户在当前编辑器里敲键盘"的方式修改——例如格式化、保存时重写、其他插件或外部工具改文档、从磁盘重载。

**【现在会发生什么】**

- 文档变更回调里直接执行"哪些批注受影响 → 删除 → 撤回对应聊天草稿 → 通知预览刷新"。
- 撤回与刷新最终会触达界面对象(聊天窗口、JCEF 预览),而这些界面通道要求运行在 IDE 的 UI 线程上,并且有显式断言。
- 文档变更回调运行在"执行这次修改的线程"上,不保证是 UI 线程。后台写入时就会触发断言/异常,异常还会从文档回调抛回写入方;即使不抛,也可能在非 UI 线程碰 Swing。
- 服务层在持有自身锁的同时调用界面通道,还会扩大锁与 UI 的交叉窗口。

**【使用影响】**

- 后台只见日志里的异常,普通用户可能遇到格式化/保存后自动撤回没有生效,或偶发的界面卡顿;这类问题难以复现、难以归因。
- 对于"自动删除"这种默认开启的能力,触发面比想象中大。

**【证据】** 撤回通道要求 UI 线程(ClaudeSDKToolWindow.java:263);文档变更回调内直接触发删除与撤回(MarkdownReviewService.java:413-430);撤回实现遍历批次并调用界面推送(:643-681);项目级刷新广播(:749-762)。

**【修复方向(抽象)】**

1. **服务层只做数据决策**:判断"哪些草稿需要撤回",不在任何线程上直接触达 UI。
2. **通知统一交给 UI 调度层**:由调度层负责合并、排队、切到 UI 线程后再触达聊天/预览;文档回调只负责提交"待处理事件"。
3. **锁与 UI 解耦**:界面通知不在服务锁内执行,避免"后台写文档持有服务锁、UI 等锁"的交叉等待。

**【建议】** 采纳。验收标准:后台线程修改文档时不出现线程断言异常;自动撤回仍然及时生效;UI 线程不因后台写入被长时间阻塞。

**【修复后的样子】** 格式化、保存重写、其他插件或外部工具改文档时,自动删除与草稿撤回照常完成,不再出现线程断言异常,也不会因为这些后台写入让界面卡顿。

**【影响与代价】** 撤回/刷新通知可能比现状晚一个毫秒级的调度周期,用户无感;服务锁与界面通道解耦后,后台写入与界面操作的相互等待减少。代价是多了一层异步调度,需要测试覆盖"通知一定会到达"。

### R5(P1)原文被改坏后,批注在预览里静默消失,但永远不会被清理,自动草稿也仍会发送

**【功能】** 批注的定位与"失联"状态处理;autoAddToChat 的撤回规则。

**【触发场景】**

- 关闭 autoDeleteAffected(用户选择"原文被改也保留批注"),然后编辑批注覆盖的那段原文(哪怕只是改一个字、随后又撤销);
- 或把一条**已完成**的批注所在原文改掉。

**【现在会发生什么】**

- 后端把无法再唯一定位的批注标记为"失联",但下发给预览的列表**只包含仍能定位的批注**。
- 当前定位规则要求**整段原文仍然唯一存在**(必要时还要前缀/后缀上下文)才算"还在";哪怕只改了整段里的一个字、随后又撤销,也会被判为失联。实际上批注的"头锚点"(开头那段文字及其上下文)通常还在。
- 于是这条批注从预览里凭空消失:看不到高亮、看不到列表项,也没有删除入口;它却仍然留在内存状态里,persist 开启时继续写进工作区文件。
- 位置核对会跳过已失联的批注,所以即使把原文改回来,它也不会复活。
- 浮层其实已经写好了"原文位置已变化"/"无法定位"的展示与按钮状态,但后端从不下发这类条目,这些界面成了死代码。
- 自动草稿侧只把"已完成"视为失效,失联但未完成的批注仍算"有效",因此它的自动草稿不会撤回——用户看不到这条批注,发送时它仍会进入给 AI 的消息。

**【使用影响】**

- 用户认为自己保留了批注(autoDelete 关闭),实际批注已悄悄消失且无法找回/删除。
- "预览里看不见、聊天里仍会发出去"是最容易造成误解的组合:AI 收到的要求,用户无法在预览中核对来源。
- 状态只增不减,长期使用后内存与工作区文件持续膨胀。

**【证据】** 下发列表只含可定位批注(MarkdownReviewService.java:220-228);定位要求整段原文匹配、失败即失联(MarkdownReviewService.java:341-380,其中 :346、:351-355;AnnotationAnchorResolver.java:7-31);"有效批注"判定只看完成状态(:684-691);浮层失效态界面与文案(index.ts:337-349;labels.ts 的 stale/orphaned)。

**【修复方向(抽象)】**

1. **先分层定位,再谈失联(2026-10-29 已拍板)**:定位按"整段原文 + 上下文" → "头部锚点(选中的开头片段 + 上下文校验)" → "尾部锚点(选中的结尾片段 + 上下文校验)"逐级尝试。**只要任一片段锚点仍能匹配,就认为批注还在**:唯一匹配时保留为"原文已变化"状态,高亮/标记挂在锚点上,原文快照与批注内容不变,用户可继续查看、编辑、删除或重新定位。只有所有片段锚点都找不到时,才视为真正失联;**出现多处候选(歧义)不算"不存在",不自动删除,保留为可见失效态由用户处理**。前后上下文只用于消歧,不能单独作为"批注还在"的依据——否则整段被替换、只剩周围文字相同时会被误保留。
2. **自动删除的触发条件同步改变(2026-10-29 已拍板)**:autoDeleteAffected 不再以"编辑区间碰到批注"为删除条件,而以"**所有片段锚点都不存在**"为删除条件。区间内的局部修改、换行、重排,只要任一片段锚点还能匹配,就不自动删除,保留为"原文已变化";片段锚点匹配到多处(歧义)时同样不自动删除,保留为可见失效态;只有所有片段锚点都不存在时,才按设置删除(开,仅未完成批注)或显示为失效态(关,或已完成批注)。设置文案需要同步改成"彻底无法定位时才自动删除"。
3. **真正失联的归宿**:二选一 —— 可见的失效态(推荐) / 自动归档清理;两者都撤回其自动草稿。
4. **不得"隐藏 + 保留"**:既不在界面上出现、又永久留在数据里,是最差的组合。下发给预览的列表必须包含"原文已变化"状态,否则修复后会以另一种形式重新变成"隐藏"。
5. **撤回规则统一**:删除、完成、所有片段锚点都不存在、归档 → 撤回其自动草稿;仍能匹配到锚点的批注(包括"原文已变化"和"歧义"两种可见态)**不撤回**(用户能在预览里看见);发送前的过滤继续作为双保险。
6. 清理要有可解释的规则(何时、依据什么),避免用户内容无声消失。

**【建议】**(2026-10-29 已拍板)采纳"多锚点仍在即保留"的分层定位;autoDeleteAffected 改为"所有片段锚点都不存在时才删除";歧义不强行归属、也不自动删除,保留为可见失效态;真正失联的批注以"可见的失效态 + 可删除 + 撤回自动草稿"处理。

**【修复后的样子】** 编辑批注覆盖的原文时,只要任一片段锚点(首选头部锚点)还能匹配,这条批注就**继续存在**:以"原文已变化"状态显示在预览里,高亮挂在仍可定位的锚点上,原文快照和批注内容保留,用户可查看、编辑、删除;**不会被 autoDeleteAffected 自动删除**,它的自动草稿也不会被撤回。只有所有片段锚点都不存在时,才进入最终归宿:未完成批注按设置自动删除(开)或显示为可见失效态(关),已完成批注始终保留为可见失效态;若锚点匹配到多处(歧义),保留为可见失效态、不自动删除;仅在真正失联/删除时同步撤回自动草稿——不会再出现"预览里看不到、聊天里却发出去了"。

**【影响与代价】** 绝大多数"改了一个字/挪了一段/插了一个换行"的情况不再丢批注,只有所有片段锚点都不存在时才会被自动删除(未完成批注)或转为可见失效态(已完成批注);锚点匹配到多处时保留为可见失效态、不删除。预览里可能出现更多"原文已变化/歧义"条目(可用筛选/折叠控制显示)。autoDeleteAffected 的含义从"碰到就删"变成"彻底找不到才删",设置文案和用户预期都要同步调整。片段锚点必须要求"能唯一定位才归属":开头/结尾片段在文中多处出现时宁可不匹配,也不能把批注挂到错误位置。若选归档路径,失效批注直接消失且草稿撤回,状态不再增长,但用户失去最后查看的机会。

**【补充:换行/空白算不算内容修改】**(2026-10-29 批注确认)

- 换行、空格等插入/删除如果发生在批注区间**之外**(包括正好落在区间的起止边界),**不会丢失批注**;区间只是随编辑平移,按"位置变化"刷新,不触发自动删除。边界插入的安全性已有单测覆盖(`trimsWholeFileRewritesAndKeepsBoundaryOrUnrelatedEdits`)。
- 如果换行落在批注区间**内部**(在选中的文字中间按 Enter,或格式化工具在选区内部重排),被批注的原文确实变了;但按本轮"多锚点保留 + 自动删除条件改变"的决策,**只要任一片段锚点(首先是头部锚点)还能匹配,批注就保留为"原文已变化",不会自动删除**。只有所有片段锚点都不存在时,才按 autoDeleteAffected 的设置处理(开:删除;关:显示为失效态);锚点歧义时保留为可见失效态、不删除。
- 因此,换行只有在"把批注依赖的锚点也一起破坏"时才会导致删除;单纯在选区内部换行、而开头/结尾文字还在,批注会保留并标记为"原文已变化"。
- 整文件级别的换行符转换(CRLF↔LF)或重排:如果批注选中的文字本身跨行,换行符变化会被视为内容变化;如果批注只选中不含换行的文字,即使文件其他位置换行或重排,只要原文仍唯一存在,就保留。
- 已完成批注不受 autoDeleteAffected 删除,彻底失联时也保留为可见失效态;当前实现会在原文变化后把它隐藏,同样由本轮 R5 修复。

**【歧义/原文已变化的界面与处置】**(2026-10-29 批注确认)

| 状态 | 在哪里显示 | 用户能做什么 |
| --- | --- | --- |
| 原文已变化(唯一匹配) | 正文里在匹配到的片段上画高亮/标记,样式与正常批注区分(虚线或警示色);同时在批注列表里带"原文已变化"徽标 | 查看、编辑、删除;也可以重新选择原文重新关联 |
| 无法唯一定位(歧义) | **不在正文画任何高亮/标记**(避免挂到错误位置);只在顶部控制条的状态入口和批注列表里显示,带"无法唯一定位"徽标 | 重新定位(主路径)、删除、查看原文快照;候选跳转为可选增强 |

补充说明:

- **入口必须显眼**:顶部控制条显示类似"N 条批注 · M 条待确认"的计数/警告图标;点击打开现有批注列表。不能让这些条目只存在于数据里(否则又变成"隐藏 + 保留")。
- **列表内容**:每条显示状态徽标、原文快照、批注内容、最后已知文件与行号;歧义条目没有单一位置,因此不提供"定位原文",只提供"重新选择原文"。
- **重新定位的主流程**:在条目上点"重新定位" → 浮层进入选择模式 → 用户在预览里选中正确的文字 → 确认关联 → 批注恢复到"已定位",批注 id 与内容不变;若它在聊天草稿中,按现有"编辑批注"的规则更新草稿快照。
- **删除**:与普通删除一致,同时撤回其自动草稿。
- **未处理时**:条目保留在列表与草稿中,不会被自动删除;发送时仍使用冻结的原文快照;批量"加入 CC GUI"会包含它们,但顶部"待确认"计数会提示先核对。
- **可选增强(第一版可以不做)**:歧义条目列出候选位置(行号),点击在编辑器里跳转查看,确认后再走"重新选择原文";不要自动替用户选一个候选。
- **验收**:歧义与变化条目都能从界面看到并处置;处置后状态清除;未处置不自动删除;任何情况下都不把批注挂到用户未确认的位置。

### R6(P2)部分"目标已变化"的错误仍显示为笼统的"操作失败"

**【功能】** 浮层操作失败时的提示。

**【触发场景】**

- 一条批注在另一个预览里被改过/删掉,当前预览还拿着旧操作去更新;
- 点"定位原文"时,原文刚刚被改坏,批注已不再处于可定位状态。

**【现在会发生什么】**

- 后端在"按当前文件查找目标批注"时找不到(因为列表只含可定位批注),于是走到一个通用异常分支。
- 浮层收到的是"操作失败",不是"这条批注已过期/已不存在",用户不知道下一步该重选、刷新还是重新添加。
- "定位原文"分支里本来写了"原文已无法唯一定位"的检查,但因为能走到那里的批注必然是可定位的,这个检查永远不会触发,属于死代码。

**【使用影响】** 用户遇到的是"失败但不知道怎么办";排障时也无法区分是并发修改、定位失效还是系统错误。

**【证据】** 通用异常与错误键映射(NativeMarkdownAnnotations.java:255-276、:304-314);下发列表只含可定位批注(MarkdownReviewService.java:220-228)。

**【修复方向(抽象)】**

1. **按"用户下一步能做什么"给错误分类**:已过期 → 刷新/重新选择;已不存在 → 重新添加;文档已变 → 等待预览;系统错误 → 重试/反馈。
2. 后端只传语义,不传展示文案;浮层用既有词典翻译(第一轮已定的通道)。
3. 删除不可达的分支与死检查,避免误导维护者。

**【建议】** 采纳。验收标准:所有"目标变化"类失败都显示可操作的提示,不再出现通用"操作失败"。

**【修复后的样子】** 操作过期批注时,提示会明确告诉用户"这条批注已被修改/已不存在/文档已变化",并引导下一步(刷新、重新选择、重新添加);不再出现"操作失败"这种无从下手的提示。

**【影响与代价】** 纯体验与可维护性改善,不改变任何正常路径的行为;新增的错误分类需要与浮层词典保持同步(第一轮已建立键化通道)。

### R7(P2)预览页面重载后,浮层可能第一帧不出现

**【功能】** 浮层与预览页面的连接建立。

**【触发场景】** 预览页面重新加载或重建(切换预览设置、主题、手动刷新等),但浮层组件实例没有被重建。

**【现在会发生什么】**

- 新页面启动后会向后端发"就绪"。
- 后端收到"就绪"后走一次完整刷新,但"状态未变就不发"的影子比较仍在生效;新页面的状态与上一帧完全相同(同一文档、同一份批注、同样的版本号),于是**一帧都不发**。
- 浮层脚本收不到任何状态,界面保持隐藏,直到用户下一次编辑或操作才恢复。

**【使用影响】** 用户重载预览后以为功能坏了;这类"看起来是偶发"的问题很难被主动发现。

**【证据】** 就绪/同步处理(NativeMarkdownAnnotations.java:204-213);影子比较与早退(:454-489)。

**【修复方向(抽象)】**

1. 把"页面就绪"定义为**必须应答**的事件:就绪后无论状态是否与上一帧相同,都下发一次完整状态。状态推送本身是幂等的,多发一帧的代价可以忽略。
2. 影子比较只用于"主动变更"的抑制,不用于"应答请求"。

**【建议】** 采纳。验收标准:用任意方式重载预览后,浮层立即恢复,不依赖下一次编辑。

**【修复后的样子】** 无论主题切换、预览设置变化还是手动刷新,浮层在页面就绪后立即恢复,不需要用户再编辑一次文档"唤醒"它。

**【影响与代价】** 每次页面就绪多发一帧完整状态(幂等,成本可忽略);影子比较继续用于抑制主动变更造成的重复推送,职责更清晰。

### R8(P2)文档监听与文档引用在项目生命周期内不释放

**【功能】** 批注位置跟踪。

**【触发场景】** 长时间使用、打开/关闭大量带批注的 .md;或关闭功能后继续编辑曾经带批注的文档。

**【现在会发生什么】**

- 一个文档第一次被跟踪时注册一次变更监听;之后无论该文档上的批注是否已全部删除、文件是否关闭,监听器与文档引用都不会解除。
- 关闭功能后,这些监听器仍然存在:每条编辑仍会做一次批注区间核对(虽然不再推送内容)。
- 文档被强引用后无法被缓存回收;批注越多、文件越大,项目会话期间占用越高。

**【使用影响】** 长会话内存缓慢增长;关闭功能后仍保留少量按键成本;与"资源随内容回收"的预期不符。

**【证据】** 文档集合与只加不删的监听(MarkdownReviewService.java:65、:390-392);关闭状态下的编辑核对(:395-410);服务销毁时才清理(:768-776)。

**【修复方向(抽象)】**

1. 监听与位置跟踪的寿命绑定到"该文档当前是否还有批注":最后一个批注移除即解除,重新有批注时再建立。
2. 功能关闭时不注册、不执行这些跟踪。
3. 文档关闭/删除时释放对应引用与位置标记。

**【建议】** 采纳。验收标准:删除某文件全部批注后,该文档不再参与编辑回调;功能关闭后编辑不产生批注区间核对。

**【修复后的样子】** 删除某个文件的最后一条批注后,该文档不再被监听、不再参与位置核对;关闭功能后编辑文档也不再触发批注相关计算。长时间使用、反复打开大文件时,内存不再随"历史上出现过的文件数"增长。

**【影响与代价】** 对仍有批注的文件行为完全不变;重新给文档加批注时会重新建立跟踪,成本很小。极端情况下(最后一个批注删除后立刻重建)会有一次重建开销,可忽略。

## 3. 修复后的整体状态与影响

### 3.1 场景前后对比

| 场景 | 现在的样子 | 修复后的样子 | 用户能否感知 |
| --- | --- | --- | --- |
| 开启功能,在长文档里连续输入 | 每键一轮位置核对 + 全量序列化 + 全文图表扫描 + 推送 | 以原生预览刷新完成为锚点:连续输入期间只同步落后状态,原生预览追平后再完整刷新;无批注文件不产生完整刷新 | 能:打字更跟手,高亮在原生预览刷新完后立即跟上 |
| 关闭功能后继续编辑 | 仍有每键"预览→后端"往返与核对 | 零桥接工作 | 基本无感,关闭真正等于零成本 |
| 同时打开多个预览,编辑其中一个 | 其他预览各自序列化一遍状态(只是不发包) | 与本次编辑无关的文件直接跳过 | 多预览场景更稳 |
| 把批注加入草稿后关闭聊天标签 | 草稿变"幽灵",占配额,persist 时跨重启累积 | 立即回收;其他聊天不受影响 | 能:关闭标签等于放弃未发送草稿(需提示) |

| 格式化/外部工具修改文档 | 可能触发线程断言异常,自动撤回偶发失效 | 通知统一切到界面线程,撤回可靠 | 间接:异常日志消失,行为更稳定 |
| 修改/撤销批注覆盖的原文(含在选区内换行) | 整段原文一变就判失联:开启自动删除时直接删除,关闭时从预览消失但数据残留;自动草稿仍会发送 | 任一片段锚点还能匹配就保留为"原文已变化"并可见,**不自动删除**;锚点歧义保留为可见失效、不删除;所有片段锚点都不存在才按设置删除/失效,并撤回草稿 | 能:轻微修改和换行不再丢批注;所见即所发 |

### 3.2 会发生的行为变化(需要用户知道)

- 关闭聊天标签将放弃该标签未发送的批注草稿(IDE 重启不在此列;仍打开的标签仍会恢复)。
- 原文被改坏的批注不再"隐身":只要任一片段锚点还能匹配就保留为"原文已变化"并可见,**不自动删除**;只有所有片段锚点都不存在才按设置进入失效态/删除,并撤回其自动草稿;锚点歧义时保留为可见失效态、不删除。
- autoDeleteAffected 的含义改变:从"编辑碰到批注范围就删"变为"彻底无法定位才删";选区内部换行、局部修改不再触发删除,设置文案会同步更新。
- 歧义批注不会出现在正文高亮里,而是在顶部"待确认"计数与批注列表中显示,可重新选择原文或删除;"原文已变化"的批注在正文中以区分样式显示。
- 配额上限提高到 500;满额时先回收孤儿草稿,仍满则提示"草稿已满(500),请先提交批注或清理草稿",不再静默挤掉别的草稿。
- 预览重载后浮层会立即出现;错误提示会具体到"下一步怎么做"。
- 2023.3–2024.2 用户会看到版本要求说明。

### 3.3 不变的部分

- IDE 自带的 Markdown 渲染、滚动、缩放不受影响;我们只影响叠加的批注浮层。
- 批注的定位、高亮、完成/删除、手动加入/引用、10 种语言、persist 开关语义、聊天消息格式均保持现状。
- 默认关闭、autoDeleteAffected 默认开启等默认值不变。
- "首次开启功能后,已打开的预览需要重开一次"的既有约束不变(如果产品愿意,可作为后续优化)。

### 3.4 代价与风险

- 连续输入时,覆盖层会等原生预览刷新完成后再更新;页面落后期间高亮本来就隐藏,视觉上无新增延迟。合并窗口只是可选的合并优化,不会引入新的可见延迟。
- "关闭标签=放弃草稿"是产品语义变化,需要在关闭确认中提示;若用户期望恢复,需要走独立的持久登记方案。
- 展示失效/变化批注会增加列表条目,需要提供筛选或折叠,避免日常视图变吵。
- 自动删除变得更保守:原来"碰到就删"的失效条目现在会以"原文已变化"保留下来,习惯自动清理的用户会看到更多保留项;设置文案必须同步,否则用户仍按旧语义理解。
- 头部锚点匹配必须要求"唯一":开头片段在文中多处出现时宁可不匹配,也不能把批注挂到错误位置;这条规则需要专门的正反例测试。
- 配额提高到 500 后,持久化记录的条数上限同步变大;已有的"总字节预算"观察项仍需单独评估。
- 满额拒绝路径需要 UI 配合,否则用户只知道"加不进去"。
- 通知调度层引入异步性,需要测试保证"通知最终一定到达"。
- 每项都需要回归测试(单测 + 沙箱冒烟),尤其是 R1 的性能验收需要可观测计数,不能只靠体感。

### 3.5 工程层面的收益

- 刷新入口收敛为一处,后续新增触发源不会再次绕过影响判断。
- 监听/跟踪寿命与数据绑定,资源模型更可解释。
- 错误从"通用失败"变为语义分类,浮层词典成为唯一展示来源。
- 草稿配额只回收无主数据,存储与真实草稿一致。
- PR 拆分后,性能、生命周期、交互与收尾可以独立评审和回滚。

## 4. 决策摘要(2026-10-29 已拍板)

**本轮已确认**

- R1:以"原生预览刷新完成"为锚点,追平前只同步落后状态,追平后一次完整刷新;合并窗口只是可选优化,不再是产品决策。
- R2:关闭状态在桥接入口短路。

- R4:服务层只做数据决策,UI 通知统一调度。
- R5:分层定位——整段原文优先,其次头部/尾部片段锚点,上下文只用于消歧;**任一片段锚点匹配即保留**为"原文已变化"可见态,不自动删除;歧义保留为可见失效态、不删除;只有所有片段锚点都不存在才按设置删除/失效,并撤回自动草稿。autoDeleteAffected 的含义同步改为"彻底无法定位(锚点不存在)才删除"。
- R6:错误按"用户可采取的动作"分类。
- R7:就绪强制下发一帧。
- R8:监听/跟踪寿命绑定到"是否还有批注"。
- R9:收尾项批量处理。

**实现细节(不阻塞拍板)**

- 合并窗口长度:默认 100–200ms,仅用于合并连续推送;如果"原生预览追平"本身已经足够合并,可以省略。
- 头部锚点的长度与上下文窗口:按"能唯一定位"动态取值,具体值在实现与测试中确定;出现多处候选时不强行归属。

## 6. 总体验收标准(业务视角)

1. **开启后连续输入**:后端的"完整刷新"次数不随文档大小、批注数量增长;无批注文件不产生完整刷新;覆盖层以原生预览刷新完成为锚点,不抢在原生预览之前。
2. **关闭后编辑**:不产生桥接工作,或虽有请求但零工作量。
3. **关闭聊天标签**:配额(500)与持久状态中不再残留该标签的未发送草稿;满额时先回收孤儿,仍满则拒绝并提示,不静默丢弃活跃草稿。
4. **后台改文档**:无线程断言/异常;自动删除与撤回仍生效;UI 不被长时间阻塞。
5. **失联批注**:任一片段锚点仍在的批注保留为"原文已变化"并可见、不自动删除;锚点歧义保留为可见失效、不删除;所有片段锚点都不存在的批注可见/可删或归档,并撤回其草稿;不再出现"预览里看不到、聊天里仍会发给 AI"的组合;状态不无限增长。
6. **目标变化类失败**:提示可操作,不再是通用"操作失败"。
7. **重载预览**:浮层立即恢复,不依赖下一次编辑。
8. **资源回收**:删除全部批注后文档不再被跟踪;关闭功能后不执行批注核对。
9. **收尾项**:版本提示、常量、废弃 API、PR 瘦身逐条核对完成。

## 7. 与第一轮文档的关系与修正记录

1. **§1b 的"轻量推送"表述需要修正**:第一轮记录为"PR-1 实施实际省略了合并窗(每键一帧轻量推送)"。复核发现"编辑事件"路径确实是轻量/可短路的,但"预览回传同步"路径仍走完整刷新(含全文图表扫描),因此"每键一帧轻量推送"整体上不成立。本轮的 R1 即补齐这半条。
2. **§2 方案 B 的前提需要修正**:第一轮以"关闭标签后,reviewTargetId 会被存档、重开标签可恢复"为依据选择"关标签懒回收"。实际关闭路径会先删除该标签的存档,重开标签是新身份,旧草稿无法恢复。R3 需要重新拍板。
3. **§13/§17 的"三层驱逐"需要收紧**:第三层会淘汰活跃草稿,与"不静默丢用户可见数据"冲突。**本轮已拍板移除第三层**:只保留"已终态/无主草稿"回收,满额且无可回收数据时拒绝新增并提示;上限同时提高到 500。
4. **§18 的瘦身结论范围**:已核对,hardening 计划与实施附录确实只存在于 docs 分支;但最初的 410 行开发计划文档仍在功能分支,属于本轮 R9 的处理范围。
5. **§17 记录为可接受的余项**:选择聊天弹窗英文文案仍保留(如需本地化需接入 IDE 自己的资源通道);批注列表本身无配额属用户内容,本轮不改变。
