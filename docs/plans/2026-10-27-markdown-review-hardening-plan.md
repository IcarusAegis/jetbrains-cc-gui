## 0. 功能地图:这个功能是什么、入口在哪

**IDE 原生 Markdown 预览批注**,由三部分组成:

| 部分 | 在哪 | 干什么 |
| --- | --- | --- |
| **预览浮层** | IDE 自带的 Markdown 预览面板(编辑 .md 文件时分屏渲染出的 HTML) | 注入 JS/CSS,在渲染结果上叠加工具条、弹窗、高亮。文件本身的渲染始终由 IDE 负责,我们只叠浮层 |
| **Java 服务** | IDE 端,项目级服务 | 保存批注(原文位置、内容)、4 个设置开关、"待发草稿批次"(批注加入聊天时先登记,等聊天前端确认) |
| **聊天前端** | CC GUI 工具窗的输入框 | 已加入的批注显示为输入框上方的草稿卡片,可逐条移除;发送时打包进消息 |

**入口在哪**(功能默认**关**,没在设置页开启就什么都看不到——这可能是你没见过它的原因):设置页勾选"启用 Markdown 预览批注(beta)"后:

- 在**预览渲染出的 HTML 里**(不是编辑器里)选中一段文字 → 弹出操作条:"批注"(添加评论)、"引用到 CC GUI"(把原文直接塞进聊天草稿);
- 每条已保存的批注,在渲染内容上**常驻显示**高亮框,点高亮可查看/编辑/删除/定位原文/标记已完成——高亮不需要你点任何东西才出现;
- 浮层顶部有"**加入 CC GUI**"按钮:把当前文件所有未完成批注一次性加入聊天草稿;每条批注的弹窗里还有"发送此批注到 CC GUI"。

设置页 4 个开关:enabled(启用,默认关)、autoAddToChat(保存批注后自动加入聊天草稿)、autoDeleteAffected(原文被编辑破坏后自动删除对应批注)、persist(重启后保留批注和待发快照,默认关)。

## 1. 问题 1(P0):功能关闭时,在 Markdown 里打字也会被拖慢——影响所有用户

**功能**:预览浮层。**场景**:你打开一个 .md 文件的 IDE 预览(不管批注功能开没开),在编辑器里打字。

**现在会发生什么**:浮层组件在预览打开时**无条件创建,不看开关**。之后你每敲一个键,后台立刻做一轮看不见的工作:读一次磁盘上的语言配置文件、打一行日志、深拷贝全部配置和批注、把整篇 Markdown 从头到尾扫一遍找 Mermaid 图、把所有状态序列化后发给预览页面。IDE 每次刷新渲染后,浮层还会回发一次"同步"请求,后台再全文核对一遍所有批注的位置。综合下来:**一次按键 ≈ 2 轮全量状态推送 + 1 次全文位置核对**。这一轮还会**广播给所有打开着的 Markdown 预览**——改 A 文件时 B、C 的预览也各做一遍。全部发生在打字的界面线程上。功能开启时是必要成本;**关闭时是给每个用户白付的税**。

**证据**:浮层无开关检查即创建(NativeMarkdownExtensionProvider.java:12-19);每键读盘/日志/深拷贝/全文扫描/序列化(NativeMarkdownAnnotations.java:63-69、368-386;LanguageConfigService.java:91);无条件广播(MarkdownReviewService.java:428);渲染补丁后回发同步触发全文核对(index.ts 的 afterPatch 监听 + MarkdownReviewService.java:322-361)。

**1a. 开关怎么挡住这些工作 —— ✅ 已拍板:创建层门禁 + 开关文案备注**

选定路径:预览打开的那一刻看开关,关就不建浮层。配合两点:

- **关闭开关**:对已存在的浮层立即生效——后台广播一次"已关闭"状态,浮层立刻隐藏自己,此后不再有任何每键开销;
- **开启开关**:新打开的预览直接有浮层;**已经打开的预览要关掉再打开(或切到别的文件再切回)才会出现浮层——不需要重启 IDE,更不需要重装插件**;
- 设置开关的描述文字加一句备注,说明"开启后,已打开的预览需重开一次"。

(放弃的路径是"运行层门禁":浮层总是创建、随开关动态挂摘监听。它切换即时生效,但保留创建成本、且要维护两处状态一致——你已确认接受"重开预览"的体验,换取实现最简单。)

**1b/1c/1d 是三个互不依赖的子决策,各砍掉按键浪费中的一块**(白话版):

- **1b 管"多久做一次"**:现在每敲一个键就做一整轮刷新;1b 把"每键一轮"合并成"每 0.1–0.2 秒一轮",且状态没变时干脆不发。
- **1c 管"每轮里的一次磁盘读"**:每轮都要读一次磁盘上的语言设置文件;1c 把结果缓存起来,只在语言设置真的变过时才再读。
- **1d 管"通知发给谁"**:现在任何文档一变,所有打开的预览都各自再做一整轮刷新;1d 只通知状态真的变化的那个预览。

三个各管一块、互不替代:只做 1b,每轮里仍有磁盘读、仍广播给所有人;只做 1c,每键仍是一整轮;只做 1d,该刷新的那一个仍是每键一次且带着磁盘读。全部做掉,按键开销才真正下来。

**1b. 打字时的这轮工作怎么变少(防抖)**

先澄清几个容易误解的点:

- **什么动作会触发这轮工作**:只有**在 IDE 编辑器里编辑 .md 文件本身**——打一个字、删一个字、粘贴一段,每敲一个字符触发一轮。原因:浮层高亮框靠"文档第 X 到 Y 个字符"定位,你一改正文,已有批注的位置就可能移动(比如在批注前面插了几个字,高亮要跟着右移),后台要立刻重算并推送。**在浮层弹窗里写批注评论、点"添加/删除/标记完成"、把批注提交到聊天,都是一次性动作,不属于这个每键开销**。
- **"预览"指什么**:始终是 IDE 自带的那块 Markdown 渲染面板。防抖**不影响 IDE 自己的渲染**(照常实时更新),只影响**我们叠加的批注浮层**——高亮框、批注标记的位置什么时候跟上你的编辑。
- **滚动会不会不跟手**:不会。滚动、缩放、窗口变化时,浮层位置由**页面内逻辑即时重算**(不经过后端往返),防抖完全管不到它;防抖只影响"**编辑文档之后**批注位置和列表的刷新"。表现是:连续打字时高亮/标记落后 0.1–0.2 秒,停下后立刻跟上。
- **现状**(它是怎么处理的):现在**没有任何合并**——每键立即一整轮读盘→拷贝→扫描→序列化→推送;防抖方案就是把"每键一轮"变成"每 0.1–0.2 秒一轮"。

| 路径 | 表现 | 代价 |
| --- | --- | --- |
| 固定时间窗合并(100–200ms) | 后台消息量从"每键一轮"降到"每秒几轮";浮层以 0.1–0.2 秒的粒度跟上编辑 | 要引入定时器,并保证"最后一次按键后必定再刷新一次"(否则停在半路时浮层永远停在旧状态) |
| 只做内容抑制(状态没变就不发) | 编辑与批注无关的位置时零开销;连续编辑批注附近时仍每键一轮 | 无定时器,最简单;收益上限低于防抖 |
| 两者叠加 | 最优 | 两套机制、两套测试 |

**建议**:叠加,两者都不复杂。

**1c. 磁盘读怎么省(语言缓存)**

先说清这里的"语言"是什么:它指**浮层界面文字显示哪种语言**(弹窗按钮、提示语是中文、英文还是日文……),由 IDE 界面语言或你在设置里手动选择的语言决定。浮层每次刷新都要后端告诉它"现在该显示哪种语言"——**现状是没有任何缓存,每次都重新读一遍磁盘上的语言配置文件**(用户手动设置过语言时还每次打一行日志)。

| 路径 | 表现 | 代价 |
| --- | --- | --- |
| 显式失效缓存:改语言的地方主动作废 | 热路径零磁盘读、零日志 | 每条能改语言的路径都要记得作废,漏一处就是"改了语言不生效"的陈旧值 bug |
| 按文件修改时间自动失效 | 无需维护作废点 | 同一秒内的两次修改可能漏检;跨平台时间戳语义差异 |
| 监听文件变化事件 | 自动且及时 | 引入文件监听子系统,它自身的生命周期与平台差异(Windows)成为新失败面 |

**建议**:显式失效(本仓库能改语言的地方很少,枚举得住);同时把"每次调用打日志"降为一次性。

**1d. 广播什么时候发(条件通知)**

先澄清:这个"广播"**不会改动你别的文件的批注,数据也不会串文件**。A、C 文件预览显示的始终是它们自己文件的批注。发生的事只是:你改 B 文件时,A、C 的预览各自"把自己文件的状态原样再抄送一遍给自己的预览页面"——内容没变也照抄,纯属浪费工作量。修好后的表现:改 B 只刷新 B 的预览。

| 路径 | 表现 | 代价 |
| --- | --- | --- |
| 状态真的变化了才广播 | A、C 预览不再陪跑 | 保存"上一次已知状态"的影子副本用于比对(纯内存,成本可忽略) |
| 脏标记,广播后清除 | 近似效果,更轻 | 标记遗漏会静默不更新,比多发更难发现 |

**建议**:影子副本比对。

## 2. 问题 2(P0):幽灵草稿会塞满 200 条限额,把"加入聊天"整个锁死 —— ✅ 已拍板

**功能**:批注加入聊天草稿的登记机制。**场景**:你把批注加入聊天输入框后,切换了会话或关掉聊天标签页——之后某天,任何批注都加不进聊天了,提示"Review draft limit reached",界面上却找不到能删的东西。

**现在会发生什么**:批次登记后处于"等待聊天前端确认"状态;配额上限 200 条,且**只淘汰已送达的批次、不淘汰等待中的**。三个孤儿来源:换会话时前端清空草稿不回执、关标签页时收件人从此不存在、换会话时收件人身份重新生成。孤儿攒满 200 条后"加入聊天"全部失败且无界面可清理。persist 默认关时重启能清零;开启后跨重启累积,锁死是永久的。

**证据**:只淘汰非待决批次(MarkdownReviewService.java:500-509);清空无回执(useArtifactReviews.ts:40-42、114-120);身份重生成(ClaudeChatWindow.java:363);关标签页无清理(ClaudeSDKToolWindow.java:364-379)。

**✅ 已拍板的方案**(按你的设计):

1. **收件人消亡即直接通知抛弃**:聊天标签关闭、会话切换导致目标身份消失时,立即把该目标的全部批次标记废弃(丢弃方回执 + 后端主动清理双管)。安全性由你确认的这点保证:**persist 开着时,批注本体仍然在**——随时可以从批注列表重新点"加入 CC GUI"送回草稿区,清理的只是"已无人认领的交接记录",不丢内容。
2. **persist 关闭时,开关文案提示后果**:设置页该开关旁注明"关闭后,项目关闭或 IDE 重启会丢失当前批注与未发送草稿"。
3. **配额兜底保留为保险层**:万一前两层漏了,满额时淘汰最旧的等待中批次,功能永不锁死。

## 3. 问题 3(P0):把批注标"已完成"会偷偷打开你关掉的"重启保留"开关 —— ✅ 已拍板:选 A

**功能**:persist 开关 + 浮层的"标记已完成"按钮。**场景**:你在设置页明确关掉了"重启后保留",之后在预览里把任意一条批注标了"已完成"。

**现在会发生什么**:标记完成的瞬间,后台把项目的 persist **静默打开**——所有批注、引用的原文、聊天草稿批次全部写入 `.idea/workspace.xml`,设置页里你亲手关掉的开关不知何时变成了开,无提示、无撤销。

**证据**:完成操作直接改写开关(MarkdownReviewService.java:304-307;单测断言属有意设计,MarkdownCompletionTest.java:22-23)。

**✅ 已拍板:A——去掉隐式翻转**。既然用户选择了不保存,就没有保存的必要:完成状态遵循用户的 persist 选择;关 persist 的用户完成批注后重启即失(符合他们对开关的预期)。配套:设置页 persist 开关的文案写明后果(见问题 2 拍板第 2 条);更新对应单测断言。

## 4. 问题 4(P0,流程):内部 API 校验 —— ✅ verifyPlugin 已实测通过(2026-10-28)

**功能**:浮层的"格式化选文校验"借用了 IDE 的 HTML 生成器。**场景**:发布到 JetBrains 市场 → 市场在最新版 IDE(262)上自动校验,"使用内部 API"设为失败项——不过就不能发布。

**研究版本差异需不需要安装各个 IDE?——不需要**。三条不装 IDE 的路径:

1. **校验器本身就是答案**:它下载 IDE 发行包做**静态字节码分析**,不运行 IDE。把想验证的版本(如 233、243)加进校验目标即可;当前构建已配 262,本地 Gradle 缓存里已有 243 与 262 的发行包。
2. **直接拆发行包里的插件 jar 反查标注**:本次已做,见下。
3. **Markdown 插件是开源的**(intellij-community 仓库),可查每个 API 的引入记录。
4. 真实启动某个老版本 IDE 只在**最后冒烟确认**时需要一次,且是用测试沙箱按版本号自动下载,不是"安装"。

**版本核实的范围与落盘位置**(按批注补充):

- **范围**:插件声明 sinceBuild=233(2023.3)。**2020–2023.2 的版本不在支持范围**——市场不会把插件分发给它们,对更老版本做校验只会得到"低于声明下限"的结果,没有意义。有意义的核实矩阵是声明区间本身:**233(下限,校验运行中)→ 243(当前开发实测)→ 262(已通过)→ 263.*(上限声明)**。若想把支持范围扩到 2020 年代版本,那是另一个产品决策:需要评估整个插件(不止批注功能)对旧平台 API 的依赖,并下调声明下限——建议不扩,批注功能本身就依赖新版预览架构。
- **下载后落在哪里**:
  - IDE 发行包(校验和真实启动都用它):下载进 Gradle 缓存,形如 `C:\Users\13004\.gradle\caches\8.14.4\transforms\<哈希>\transformed\ideaXX-<版本>-win\`,每个约 1–2GB;
  - 真实启动的测试沙箱(测试 IDE 的配置/日志/插件):项目内 `jetbrains-cc-gui\build\idea-sandbox\<IDE 版本>\`;冒烟截图与报告:`build\native-markdown-smoke\`;
  - 校验报告:`build\reports\pluginVerifier\<IDE>\`。
- **可以被删除吗**:全部可以,随时删。Gradle 缓存里的发行包删掉后,下次校验/启动按需重新下载(代价是再下一次 1–2GB);`build\` 目录本来就是构建产物,删了下次构建自动重建。
- **最老版本(233)的校验已启动**:2026-10-28 已把 IC 2023.3.7 加入校验目标(build.gradle 校验目标列表 +3 行,含注释),后台下载运行中;结果出来即回答问题 8 的"提下限还是物理隔离"。

**证据**:8 秒固定超时(index.ts:90-94);模态选择框(NativeMarkdownAnnotations.java:295-305);每次点击新建条目导致去重失效(:184-190 + 登记去重按条目 ID 比对)。

| 路径 | 表现 | 代价 |
| --- | --- | --- |

**✅ 已拍板(2026-10-28 批注"可以")**:第三条(处理中回执,改动最小、直接消灭误报)+ 第一条(幂等兜底,防一切重复)。
